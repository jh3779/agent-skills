# split-instructions — 대형 지시서를 태그된 파일로 분할

## 핵심 원칙

> 원본 문서는 하나의 "진실"이지만, 매번 전체를 읽으면 토큰 낭비다. 목표는
> **INDEX.md 한 번만 보면 전체 구조·진행 상태를 파악**할 수 있고, **실제
> 작업엔 관련 파일 1~2개만 열면** 되게 만드는 것.

- 분할 단위는 "작업/기능" 경계(heading). 문서마다 구조가 다르므로 heading
  depth는 상황에 맞게 판단한다 — 기계적으로 항상 `##` 또는 항상 `###`을
  쓰지 않는다.
- 분할 **규칙**(heading 기준 분할 · frontmatter 태그 · INDEX.md 형식)은
  모든 프로젝트에 동일하게 적용한다. 프로젝트마다 규칙을 새로 설계하지
  않는다 — 그래야 어떤 프로젝트에서 실행해도 같은 방식으로 동작한다.
- 산출물의 **위치**는 프로젝트 관례를 따른다: 이미 `docs/`가 있으면 그
  안에, 없으면 원본 파일 옆에 둔다. `.agent/`는 건드리지 않는다 —
  `handoff` 스킬의 세션 인계 전용 디렉터리이며 이 스킬과 용도가 다르다.
- **원본은 함부로 지우거나 치환하지 않는다.** 기본 동작은 원본을 그대로
  둔 채 분할본을 추가하는 것. 원본을 배너/스텁으로 바꾸는 건 사용자가
  명시적으로 동의했을 때만.

## 디렉터리 구조 (기본값)

원본이 `<project>/<FOO>.md`라면:

```
<project>/
  <FOO>.md                      # 원본 유지 (기본) — 상단에 분할 안내 배너만 추가
  <foo>/                        # 분할 산출물 (원본 파일명을 소문자 slug로)
    INDEX.md                    # 태그된 목차 — 항상 먼저 읽는 파일
    01-<slug>.md
    02-<slug>.md
    ...
```

프로젝트에 이미 `docs/` 관례가 있으면 `<project>/docs/<foo>/`처럼 그 안에
만든다. 어느 쪽이든 실행 전 프로젝트의 기존 구조(README, 기존 docs 폴더,
CLAUDE.md/AGENTS.md에 명시된 규칙)를 먼저 확인해서 튀지 않게 맞춘다.

## 분할 파일 형식

각 분할 파일은 frontmatter + 원본 섹션 내용:

```markdown
---
title: <섹션 제목 그대로>
tags: [기술/도메인 키워드 2~5개]
status: done | in-progress | blocked | mixed
source: <원본파일명>#<원래 헤딩 텍스트>
---

<원본 섹션의 본문 그대로 — 요약하거나 재작성하지 않는다>
```

- `tags`: 섹션 내용에서 실제로 등장하는 기술/도메인 키워드로 추론한다
  (예: `cloud-run`, `firestore-rules`, `fcm`, `ui`). 추측성 태그를 만들어
  붙이지 않는다.
- `status`: 섹션 안의 `[x]`/`[ ]` 체크리스트 비율로 판단. 체크리스트가
  없는 섹션(설명/배경 문서)은 status를 생략한다.
- 청크가 너무 작으면(대략 5줄 미만) 상위 헤딩과 합치고, 너무 크면(대략
  300줄 이상) 하위 헤딩으로 한 단계 더 쪼갠다. 항상 균등 분할하려 하지
  말고 "이 파일 하나만 읽으면 이 작업을 이해할 수 있는가"를 기준으로
  판단한다.

## INDEX.md 형식

```markdown
# <FOO> — 목차

| 파일 | 제목 | 태그 | 상태 |
|---|---|---|---|
| [01-cloud-run-worker.md](01-cloud-run-worker.md) | Cloud Run 렌더 워커 | cloud-run, ffmpeg | in-progress |
| [02-firestore-rules.md](02-firestore-rules.md) | Firestore Rules 보정 | firestore, security | done |
```

표가 너무 길어지면(대략 30행 이상) 카테고리별 소제목으로 묶는다.

## 절차

1. 대상 문서와 프로젝트 루트를 확인한다(git root 또는 문서가 속한
   디렉터리). 대상이 불분명하면 사용자에게 확인한다.
2. 프로젝트 기존 컨벤션을 스캔한다: `docs/` 존재 여부, `.agent/` 존재
   여부(건드리지 않을 것만 확인), `CLAUDE.md`/`AGENTS.md`에 문서 구조
   관련 명시 규칙이 있는지.
3. 원본을 heading 단위로 파싱해 청크 경계를 정한다.
4. 각 청크를 분할 파일 형식으로 저장한다(원본 텍스트 보존, 요약 금지).
5. `INDEX.md`를 작성한다.
6. 원본 파일은 그대로 두고, 최상단에 짧은 배너만 추가한다:
   `> 이 문서는 <foo>/INDEX.md로 분할되었습니다. 작업 시 원본 대신
   INDEX.md를 참고하세요.`
   원본을 스텁으로 완전히 치환하길 원하는지는 반드시 사용자에게 먼저
   묻는다 — 되돌리기 어려운 건 아니지만(git으로 복구 가능) 매번 기본
   동작으로 하지 않는다.
7. 몇 개 파일로 나눴는지, 인덱스 경로, 애매해서 사람이 확인해야 할 태그/
   상태 판단이 있었는지 짧게 보고한다.

## 이후 사용 방식 (에이전트가 이 프로젝트에서 작업할 때)

- 작업 시작 시 `INDEX.md`만 먼저 읽는다. 전체 분할 파일을 다 읽지 않는다.
- 지금 하려는 작업과 태그/제목이 맞는 파일만 연다.
- 진행 상황이 바뀌면 해당 섹션 파일의 체크박스 + frontmatter `status`를
  갱신하고, `INDEX.md`의 상태 컬럼도 같이 갱신한다(둘이 어긋나지 않게).
- 새 섹션이 추가되면 다음 번호로 파일을 추가하고 `INDEX.md`에도 반영한다.

## 프로젝트 간 재사용

이 스킬은 특정 프로젝트에 종속되지 않는다(`handoff`처럼) — 어느 프로젝트
디렉터리에서 실행해도 그 디렉터리 기준으로 동작한다. 분할 **규칙**은
프로젝트마다 새로 설계하지 않고 위 형식을 그대로 재사용한다. 프로젝트마다
달라지는 건 산출물이 놓이는 **위치**(기존 `docs/` 관례 유무)뿐이다.

## 하지 말아야 할 것

- **요약해서 다시 쓰기**: 분할은 재배치이지 재작성이 아니다. 원본 문장을
  그대로 옮긴다.
- **원본 삭제/치환을 기본값으로 하기**: 명시적 동의 없이 원본을 스텁으로
  바꾸지 않는다.
- **균등 분할 강박**: 섹션이 크더라도 하나의 응집된 작업이면 억지로
  쪼개지 않는다.
- **태그 남발**: 실제로 문서에 등장하지 않는 키워드를 태그로 추측해
  붙이지 않는다.

## 관련 스킬

- `handoff`: 세션 인계용 `.agent/` 상태 문서(PROJECT_CONTEXT.md·
  HANDOFF.md·DECISIONS.md)는 이 스킬의 대상이 아니다. 이 스킬은 지시서/
  작업 문서 **본문 자체**가 너무 커졌을 때 쓴다. 두 스킬은 같은 프로젝트에
  공존할 수 있다(`.agent/`는 상태 스냅샷, 분할 산출물은 작업 명세).
