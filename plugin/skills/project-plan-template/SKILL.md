# project-plan-template — 기획 단계 템플릿

**발표에서 보여 줄 결과 장면을 먼저 정하고, 거꾸로 필요한 측정·일정·범위를 잡는 기획 템플릿**이다. 2026-10-20 발표 피드백(실사용 가능성·문제 회수·가치·결론·의미 설명)과 추가 피드백(업무 시나리오·희소 사례·도메인 이해·중간 점검·기간 내 수행 가능성)이 대부분 **기획에서 빠졌다가 발표까지 미체크로 남은 항목**이었다는 점에서 만들었다. 발표 단계는 짝 스킬 `presentation-script`가 맡는다 — 이 스킬의 산출물(결론, 가치 지표, 시나리오, 증거 목록)이 그 스킬의 입력 시트가 된다.

프로젝트에 이미 기획 규칙(AGENTS.md·CLAUDE.md·기존 기획서)이 있으면 **그 규칙이 우선**이다. 이 템플릿은 빠진 칸을 채우는 용도다.

## 핵심 원칙

1. **발표 역산.** 기획 첫 단계에서 "발표에서 보여 줄 결과 장면 3개"를 정하고, 그것을 증명할 증거(측정·시연·사용자 검증)를 거꾸로 일정에 넣는다.
2. **성공 기준은 미리 고정한다.** 사용자 가치 지표 1~2개(예: 근거를 모으는 시간, 확인해야 할 건수), 측정 방법, 기준 폭을 결과를 보기 전에 적는다. 검색 점수 같은 시스템 지표만 있으면 "가치"가 비어 있는 것이다.
3. **검증은 3계층.** ① 시스템 성능 ② 과업 성공(시나리오) ③ 사용자 가치(실사용 n명). 계층마다 담당·일정·산출물이 있어야 한다. 한 계층이 비면 비었다고 적는다.
4. **문제는 같은 장면의 결과로 닫는다.** 문제 정의의 구체 장면을 시나리오로 만들어 (입력 → 기대 출력 → 확인 행동 → 측정 항목) 시연·검증에 재사용한다.
5. **결론을 맨 앞에.** 기획서 첫머리에 한 문장 결론, 하는 일/하지 않는 일, 성공 기준을 둔다.
6. **가정은 상태를 표시한다.** ✅ 확인됨 / 🟡 가정 / ⬜ 미확인. 🟡·⬜는 발표 전에 줄이거나 "계획"으로 말한다.
7. **미체크 항목에는 처분이 있어야 한다.** 점검표에서 비어 있는 항목은 (a) 일정 슬롯을 받거나 (b) **범위 제외 결정**(이유·결정자·발표에서 말할 문구)으로 기록한다. 아무 처분 없이 발표까지 가지 않는다.
8. **마일스톤마다 게이트.** 점검표를 "발표 전 한 번"이 아니라 단계마다 `scripts/plan_gate.py`로 점검한다.
9. **공개 전환을 미리 본다.** 비밀값·열람 제한 문서·개인 이메일·라이선스·데이터 이용 조건은 나중에 공개할 때 가장 비싸게 발견된다 — 기획 단계에서 사전 점검 칸을 둔다.

10. **도메인을 이해하고 시작한다.** 기획 1주 차에 용어표·업무 흐름·규제(시간 제약)·실무자 확인 슬롯을 만든다. 도메인 이해가 얕으면 시나리오가 약해진다(발표에서 "업무 관점 부족" 지적).
11. **업무 시나리오는 일별로.** 사용자가 한 주 동안 언제 무엇을 하고, 도구가 하는 일/하지 않는 일/사람이 판단하는 곳을 표로 쓴다. 도구가 못 찾았을 때의 업무 절차(대체 경로)와 **희소 사례 시나리오**를 포함한다.
12. **평균 말고 긴 꼬리도 잰다.** 평가 계획에 층화 분석(희소·흔한 사례)을 넣되 구간 기준을 결과 전에 고정하고, 튜닝에 쓰지 않는다.
13. **WBS·역할(RACI)·시간 예산을 처음부터.** 작업 단위 ≤1~2일, 담당·완료 기준·의존·버퍼 20%. 배포·운영·프로세스·사용자 검증 행을 빼먹지 않는다(담당 미지정은 "미지정"으로 보이게). 외부 입력(사람의 표시·승인)이 필요한 작업은 **대체안과 마감 2일 전 중간 점검**을 정한다. 핵심 완성 후 확장은 **발표 D-3부터 금지**, 포기 순서를 미리 적는다. 계획 대비 실제를 주 1회 갱신한다.

## 작업 순서

1. **입력 인터뷰**(필요하면 질문 도구로): 사용자·장면, 발표일·형식, 팀 역할, 이미 정해진 범위·규칙, 사용할 수 있는 사용자 검증 자원(실사용자 접근 가능 여부).
2. **템플릿을 채운다**(`references/template.md`, 0~16절 — 13 도메인 이해, 14 WBS·RACI, 15 시간 예산, 16 희소 사례 평가 계획). 모르는 칸은 비워 두지 말고 ⬜로 적고 확인 방법을 쓴다.
3. **역산 일정을 만든다.** 발표일 → 덱 동결일 → 검증 슬롯 → 개발 → 데이터 순으로 거꾸로. 검증 슬롯이 없으면 범위 제외 결정으로 적는다.
4. **게이트 점검**: `python3 scripts/plan_gate.py 기획서.md` — 필수 절 누락, 미체크 항목, 가정 상태를 보고한다. 필수 절이 비면 사용자에게 알린다.
5. **발표 입력 시트로 내보낸다**: 한 문장 결론, 결과 장면 3개, 증거 목록(측정·시연·사용자 검증), 가치 지표 상태를 `presentation-script`의 입력 시트로 넘긴다.
6. 마일스톤마다 4를 반복하고, 결과를 기획서 하단 "게이트 기록"에 한 줄 남긴다.

## 산출물

`기획_<주제>.md` (템플릿 0~16절). 짧은 프로젝트면 0·1·3·4·5·7·9절만 채워도 된다(그 경우도 3·4·9절은 비우지 않는다).

## 하지 않는 것

- 측정하지 않은 가치를 목표로만 두고 "달성"처럼 쓴다.
- 사용자 검증을 "나중에"로 두고 일정·담당 없이 남긴다.
- 점검표 항목을 지우거나 체크해서 미체크 사실을 없앤다(범위 제외라면 결정으로 기록).
- 팀원 이름과 함께 부정적 서사를 쓴다 — 의존성·일정의 문제는 구조로 쓴다.
