# 발표 준비 템플릿

발표 준비에서 나온 피드백과 시행착오를 바탕으로 한 템플릿이다. 각 절은 SKILL.md의 작업 순서와 연결된다.

## 0. 시작 전 입력 시트
| 항목 | 내용 |
|---|---|
| 청중 / 사전지식 | |
| 시간 한도 / 발표일 | |
| 최종 덱 파일(동결일) | |
| 근거 문서·결과 파일 | |
| 사용자 검증(실사용) 결과 | 있음 / 없음(계획: 누가·언제·무엇으로) |
| 가치 지표 1개 | (예: 선례 확인 시간, 확인할 건수) |
| 라이브 시연 | 있음 / 없음, 주소·백업 |
| 열람 제한 문서 | |
| 이전 피드백 | |

## 1. 구조 (결론 먼저)
1. **한 문장 결론**: "이 ○○는 ○○를 하고 ○○는 하지 않는다."
2. **문제 → 회수 장면**: 문제를 여는 장면 한 개, 마지막에 같은 장면의 결과.
3. **청중이 가져갈 3가지**.
4. 본문 순서: 결론 → 문제 → 해결(시연 포함) → 증거(숫자+의미) → 한계 → 다음 단계 → 마무리.
5. 과정(실패·정정)은 증거 단계에 흡수하고, 부록으로 보낼 것을 정한다.
6. 구분 슬라이드는 꼭 필요한 경우에만(많을수록 과정 중심으로 들린다).

## 2. 슬라이드 규칙
- 한 장 = 한 질문. 질문을 대본 머리에 적는다.
- 구분 슬라이드: 5초 이음.
- 도형·그림은 읽는 순서를 말해 준다.
- 슬라이드 문구와 말이 다르면 말을 사실에 맞춘다(슬라이드는 요청 시에만 고친다).

## 3. 숫자 의미 표 (숫자마다 작성)
| 숫자 | 무엇을 잰 값 | 몇 개 중 | 붙은 조건 | 의미 한 문장(사용자 관점) |
|---|---|---|---|---|
| 예) 54/100 | 정답이 상위 10개 안에 든 질문 | 100 | 검색 점수(대리 평가) | 열 건만 열어 봐도 절반 넘게 정답이 든다 |

말하는 순서: **조건 → 값 → 의미**. 의미 칸이 비면 그 숫자는 부록으로 보낸다.

## 4. 사실 대조표
| 슬라이드 | 문구/숫자 | 근거 문서·파일(줄) | 일치 | 조치 |
|---|---|---|---|---|
| | | | ✅/⚠/❌ | 말로 보정 / 슬라이드 수정 요청 / 확인 필요 |

❌·⚠는 "발표 전 확인할 것"에 올린다.

## 5. 라이브 시연 진행표
| 단계 | 화면 행동 | 말 | 시간 |
|---|---|---|---|
- 시연 질문은 **서비스에 실제로 넣어 결과를 확인**하고 적는다(결과 구성·번호 기록).
- 준비: 서버 깨우기(콜드스타트), 질문 복사, 화면 모드, 백업 탭, 네트워크.
- 문제 시: 느림 / 요청 상한 / 결과 상이 / 오프라인 대응 문장.
- 시연이 끝나면 돌아올 슬라이드.

## 6. 예상 질문 은행
범주: 기술 / 데이터·평가 / 책임·보안·운영 / 사업·확장 / 팀·과정 / 회의적 질문 / 도메인 전문가 / 윤리·법.
| 질문 | 답(2~3문장) | 근거 위치 | 확인 상태 |
|---|---|---|---|
확인 상태: ✅ 근거 확인 / ⚠ 근거 못 찾음(답에 "확인하지 못했다"를 넣는다).

**답하지 못할 때의 3단계**: ① 질문을 되묻고 ② 아는 것과 모르는 것을 나누고 ③ 다음 행동("확인해서 알려 드리겠습니다")을 붙인다.
**문장 템플릿**: 미측정 → "아직 재지 못했습니다. 다음 단계입니다. 지금 확인한 것은 ○○까지입니다." / 범위 밖 → "현재는 ○○까지입니다. 말씀하신 부분은 후보입니다." / 잠정값 → "다른 사람이 다시 재 보지 않은 잠정값입니다."

## 7. 리허설과 시간
- 리허설 2회 이상, 그중 1회는 **전체 시간 실측**(시연 포함, 소리 내어).
- 모의 질문 시간: 서로 질문하고 답을 채점한다(숫자 혼동·사실 오류 확인).
- 시간표: 280자/분. 합계가 한도의 90%를 넘으면 줄일 장 순서를 미리 정한다.

## 8. 덱 동결과 협업
- 최종 덱 1개, **동결 시점** 이후 수정은 한 사람만.
- 대본·메모는 동결 후 확정, 연결은 **슬라이드 제목** 기준.
- 사전 검토 1회: 발표를 만들지 않은 사람이 처음 듣는 청중 역할.
- 역할별로 "내 파트가 결론에 기여한 한 줄"을 가져온다.

## 9. 발표 후 피드백 기록
| 피드백(원문) | 해석 | 근거(우리 자료) | 타당성 | 다음 발표 대응 |
|---|---|---|---|---|
이번 발표의 피드백(참고): **잘된 점 — 초반(문제)과 접근(방법 비교)까지는 괜찮았다(10절).** 보완점 — 실사용 가능성 / 문제를 결과로 닫지 못함 / 성능은 보이나 가치는 확인 어려움 / 결론보다 과정 중심 / UI가 정돈·직관적이지 않음 / 데이터를 보이면 의미를 설명해야 함.

## 10. 잘 통한 구간 — 유지할 패턴 (피드백에서 확인됨)
2026-10-20 발표 직후 피드백: **초반(문제 정의)과 접근(방법 비교)까지는 괜찮았다.** 이해가 끊긴 곳은 구조 설명 이후(데이터·어려움·성능)였다.

| 잘 통한 구간 | 통한 이유(추정) | 뒷구간에 쓸 방법 |
|---|---|---|
| **문제**: 신고 6건이라는 구체 장면, 5영업일이라는 시계 | 청중이 상황을 그릴 수 있고 긴박함이 생김 | 구조·성능 구간도 장면 하나(질문 하나, 카드 한 장)로 시작 |
| **접근**: 세 방법을 실제 예시(타이어, 연료탱크 번호)로 비교 | "왜 이것을 골랐나"가 눈에 보임 | 어려움·성능도 "전/후 비교 한 장면 → 선택 이유" |
| 선택의 이유를 한 문장으로 닫음 | 결론이 기억에 남음 | 구간마다 닫는 한 문장(그래서 무엇) |

**뒷구간에서 끊기는 신호**: 단계·수치가 3개 이상 연속되고 예시가 없음 / 숫자 뒤에 의미 문장이 없음 / 결과를 문제 장면으로 회수하지 않음.
**규칙**: 잘 통한 구간은 수정하지 않는다. 뒷구간을 같은 패턴(장면 → 숫자 → 의미 → 선택)으로 바꾼다. 결론 한 장은 접근 직후(방법을 고른 직후)에 두고, 이후 구간은 그 결론의 증명으로 읽히게 한다. 시연도 접근 직후에 두는 안을 검토한다.

## 11. 발표 후 추가 피드백 (2026-10-21) — 원문 요지와 반영

원문 요지(멘토): ① 컬러는 중요한 포인트를 잘 정해야 처음 보는 사람도 파악한다 ② 자료 재정리 — 기술보다 마케팅 쪽에 치중, 한 페이지가 무엇을 전하는지 바로 알 수 있는지 확인 ③ 임팩트는 있으나 무엇을 말하는지 모를 수 있다 ④ 시나리오·업무 관점이 약하다 ⑤ 사례가 적은 것도 잘 찾는지 ⑥ 도메인 이해를 높이며 진행, 중간 점검을 더 상세히 ⑦ 한정된 기간 안에 수행 가능한지.

| 피드백 | 이 스킬의 반영 | 점검 방법 |
|---|---|---|
| ①③ 색·임팩트 | 원칙 10 (강조색은 한 장에 한 곳) | `deck_audit.py` 강조색 개수 |
| ② 한 장 한 메시지 | 원칙 9 (주장 문장 제목, 5초 테스트) | 위쪽 글줄이 주장 문장인지, 처음 보는 사람 1명에게 5초 보여 주기 |
| ④ 업무 시나리오 | 원칙 11 (일별 시나리오 장, 사람/도구 분담, 도메인 용어) | 시나리오 장 존재, 도구가 못 하는 일이 적혔는가 |
| ⑤ 희소 사례 | 원칙 12 (층화 분석 한 장, 예상 질문) | 구간 기준을 결과 전에 고정했는가 |
| ⑥⑦ 중간 점검·기간 | 원칙 13 (계획 대비 실제 한 장) | 우선순위 달성일, 흔들린 곳, 다음 변경 |

**이번 발표 덱에 실제로 한 수정(예시)**: 15개 장의 위쪽 글줄을 주장 문장으로 바꾸고, 번호·보조 문구의 강조색을 떼어 장당 1곳으로 줄였으며, 업무 시나리오·희소 부품 평가·계획 대비 실제 장을 추가했다(원본은 그대로 두고 새 파일로 저장).
