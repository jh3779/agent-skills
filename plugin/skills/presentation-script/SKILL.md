# presentation-script — 발표 준비 템플릿 기반 대본 생성

발표 대본을 "말로 읽기만 하면 되는 글"이 아니라 **청중이 결론과 가치를 가져가게 만드는 글**로 쓴다. 이 스킬은 한 번의 발표 준비(결함 선례 찾기 도우미, 2026-10-20)와 발표 직후 피드백 두 차례(6건 + 추가 피드백, 2026-10-21)에서 나온 규칙을 담고 있다. 규칙의 근거는 `references/template.md`에 있다.

## 핵심 원칙 (항상 지킨다)

1. **결론 먼저.** 첫 3분 안에 "이 도구/연구는 ○○를 하고 ○○는 하지 않는다"를 말한다. 과정(실패·정정)은 "그래서 이 숫자를 믿어도 된다"는 증거로만 쓴다.
2. **문제를 같은 장면의 결과로 닫는다.** 앞에서 연 문제(예: 5영업일 안에 근거 모으기)를 마지막에 지표가 아니라 **결과 장면**으로 회수한다.
3. **숫자 한 개 = 조건 + 의미 한 문장.** 숫자를 말할 때 [무엇을 잰 값][몇 개 중][붙은 조건]을 먼저, 그다음 "그래서 사용자에게 무슨 뜻인가"를 말한다. 조건만 말하고 의미를 빼지 않는다.
4. **측정하지 않은 것은 단정하지 않는다.** 가치(시간 절감, 사용성)를 재지 못했으면 "재지 못했다 + 어떻게 잴 계획인가"로 말한다. 과장 금지.
5. **슬라이드 문구와 말이 어긋나면 말을 사실에 맞추고, 어긋남을 사용자에게 알린다.** 슬라이드를 임의로 고치지 않는다(요청이 있을 때만).
6. **용어는 처음 나올 때 한 문장으로 푼다.** 전문 약어는 대본에서 쓰지 않거나 풀어서 쓴다.
7. **모르는 것은 모른다고 쓴다.** 근거를 못 찾은 사실은 ⚠로 표시하고 답을 지어내지 않는다.
8. **잘 통한 앞부분의 패턴을 뒷부분에도 쓴다.** 청중은 "구체 장면 → 비교 → 선택"으로 흐르는 구간(이번 발표의 문제·접근)을 이해했고, 단계·수치를 나열한 뒷구간(구조·어려움·성능)에서 이해가 끊겼다. 뒷구간도 **장면(예시 하나) → 숫자 → 의미 한 줄 → 선택** 순서로 쓰고, "보고서처럼 단계 나열"이 되면 예시를 앞에 둔다. 잘 통한 구간은 고치지 않는다(`references/template.md` 10절).

9. **한 장 = 한 메시지.** 모든 내용 슬라이드는 위쪽 제목(또는 작은 글줄)이 **주장 문장**이어야 한다("Challenge 01"이 아니라 "원인 근거가 있는 리콜을 31%에서 약 78%로 올렸다"). 점검은 **5초 테스트**: 처음 보는 사람이 5초 안에 "이 장이 무엇을 말하는가"를 한 문장으로 답하는가. 임팩트(그림·색·큰 숫자)는 있는데 요지를 모를 수 있다는 지적이 있었다 — 시각 요소는 그 주장을 증명하는 것 하나만 둔다.
10. **강조색은 한 장에 한 곳.** 강조색(예: 빨강)은 그 장의 주장 또는 핵심 숫자 하나에만 쓴다. 번호·부제·보조 문구까지 모두 강조색이면 처음 보는 사람이 중요한 곳을 못 찾는다. `scripts/deck_audit.py`로 장별 강조색 개수를 센다.
11. **기술보다 업무 시나리오와 근거의 균형.** 마케팅성 장(비전·장면)만 강하고 업무 시나리오가 약하다는 지적이 있었다. 발표에는 **업무 시나리오 장 1개**(누가·언제·무엇을 쓰고, 도구가 하는 일/하지 않는 일/사람이 판단하는 곳, 일별 흐름)와 **도메인 용어 풀이**(처음 보는 사람 기준)를 넣는다. 시간 절감처럼 재지 않은 값은 가설로 표시한다.
12. **평균이 아니라 경계 사례도 말한다.** 희소 사례·긴 꼬리(사례가 적은 경우)에서의 성능, 실패하는 질문의 공통점을 예상 질문 은행에 넣는다(층화 분석 결과가 있으면 한 장으로).
13. **기간 안에 가능했는가를 보여 준다.** 계획 대비 실제(일정·우선순위 달성일·흔들린 곳·다음에 바꿀 것) 한 장. 개인별 시간 기록이 없으면 적지 않는다.

## 입력 수집 (먼저 묻거나 확인)

- 청중(직무·사전지식), **발표 시간 한도**, 발표일
- **최종 덱 파일**(동결 여부), 근거 문서·결과 파일 위치, 사용자 검증(실사용) 결과가 있는지
- 라이브 시연 여부, 시연 환경(주소·백업)
- 이전 피드백(있다면) 원문
- 열람 제한·비공개 문서가 있는지(있으면 대본·메모에 출처를 노출하지 않는다)

덱이 여러 버전이면 **어느 파일이 최종인지 먼저 확인**한다. 최종 파일이 바뀔 수 있으니 슬라이드는 번호가 아니라 **제목으로 찾는다**.

## 작업 순서

0. **덱 점검(요청이 있을 때)**: `scripts/deck_audit.py 덱.pptx`로 장별 강조색 수·위쪽 글줄(주장 문장인지)을 확인하고, 5초 테스트에 걸린 장을 목록으로 사용자에게 보여 준다. 슬라이드 수정은 사용자가 요청했을 때만 하고, 원본은 건드리지 않고 새 파일로 저장한다.
1. **덱을 읽는다(읽기 전용).** `scripts/pptx_notes.py dump 덱.pptx`로 슬라이드별 제목·본문·기존 메모를 뽑는다. 구분 슬라이드·부록 유무, 시연 슬라이드 유무를 기록한다.
2. **잘 통한 구간을 먼저 확인한다.** 이전 피드백에서 "괜찮았다"고 한 구간이 있으면 그 구성(장면·비교·긴박함 장치)을 기록하고 유지한다.
3. **메시지를 먼저 정한다.** (a) 한 문장 결론, (b) 문제 → 회수 장면, (c) 가치 지표(재었나/못 재었나), (d) 청중이 가져갈 3가지. 이 4개를 사용자와 합의한 뒤 대본을 쓴다.
4. **사실 대조표를 만든다.** 슬라이드 문구·숫자 ↔ 근거 문서·결과 파일. 불일치와 ⚠를 따로 모은다(`references/template.md` 4절 양식).
5. **슬라이드별 대본을 쓴다.**
   - 한 장 = 한 질문에 답한다(질문이 없으면 부록 후보).
   - 구분 슬라이드는 5초짜리 이음 문장.
   - 숫자는 원칙 3, 용어는 원칙 6.
   - 길이는 한국어 **공백 제외 280자/분** 기준으로 시간표를 만든다(`scripts/script_time.py`).
   - 배정 시간 합계가 한도의 **90%를 넘으면** 줄일 슬라이드 순서를 미리 적어 둔다.
6. **라이브 시연이 있으면** 시연 진행표(단계·화면 행동·말·시간)와 발표 5~10분 전 준비, 문제 시 대응을 쓴다. **시연 질문은 실제 서비스에 넣어 결과를 확인한 뒤** 적는다(확인하지 못했으면 그렇게 표시).
7. **마무리**: 결론 반복 + 문제 회수 + 한계 한 줄 + 다음 단계. 약속을 반복하지 말고 **지키려고 한 일 + 결과 숫자**로 쓴다.
8. **예상 질문 은행**을 만든다(`references/template.md` 6절): 범주별(기술·데이터/평가·책임/보안·사업·팀/과정·회의적 질문), 각 답은 2~3문장, 근거 위치, ⚠. "모르는 것에 답하는 문장" 템플릿을 포함한다.
9. **발표 전 점검표**를 만든다: 슬라이드-말 불일치, 재현 전 수치, 열람 제한, 시연 준비, 시간 실측.
10. 산출물을 사용자가 요청한 곳에 쓴다(마크다운 파일, Notion, 슬라이드 메모).

## 산출물 기본 형식 (마크다운)

`발표대본_<버전>.md`:
1. 머리말: 기준 덱, 기준일, 시간 요약, 이전 판에서 바뀐 것
2. 시간표(슬라이드 · 배정 · 글자 수 · 말하기 시간)
3. 슬라이드별 대본 + 필요한 곳에만 `*(메모: …)*`
4. 라이브 시연 진행표(있을 때)
5. 사실 대조표·불일치 목록
6. 예상 질문과 답
7. 발표 전 확인할 것(체크리스트)

## PPT 발표자 메모에 넣을 때 (요청이 있을 때만)

- 슬라이드 본문은 건드리지 않는다. `scripts/pptx_notes.py add 덱.pptx 메모.json`을 쓴다(제목으로 찾기, 백업, 잠금 파일 확인).
- **PowerPoint가 파일을 열고 있으면**(폴더에 `~$` 잠금 파일) 그 창에서 저장하면 메모가 사라질 수 있다 — 사용자에게 닫고 다시 열도록 안내한다.
- 메모에 넣지 않는다: 열람 제한 문서의 출처·이름, 내부 논의, 팀원 개인을 겨냥한 문장.

## 하지 않는 것

- 근거 없는 수치·사례를 대본에 넣는다.
- 시간 단축·성능 향상 등 가치를 재지 않고 단정한다.
- 팀원 이름과 함께 부정적 서사(누가 늦었다 등)를 쓴다 — 어려움은 구조의 문제로 쓴다.
- 최종 덱이 확정되지 않았는데 번호 기준으로 대본을 확정한다.

## 발표 후

피드백을 `references/template.md` 9절 양식으로 기록하고, 이 스킬의 원칙·체크리스트에 반영할 것을 사용자에게 제안한다(스킬 파일은 사용자가 승인한 뒤에 고친다).
