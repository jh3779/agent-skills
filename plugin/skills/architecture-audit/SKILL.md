# architecture-audit — 설계 견고성 감사

## 목적과 범위

프로젝트의 **설계 결정 자체가 얼마나 견고한지**를 근거(파일 경로·코드 인용)와 함께
평가한다. "파일이 어디 있는가"(`structure-audit`)가 아니라 "이 데이터 모델·계약·상태
전이가 실제로 맞물려 돌아가는가"를 본다.

- 코드를 **수정하지 않는다** — 조사와 보고만. 수정은 사용자가 명시적으로 요청할 때만 별도로.
- `structure-audit`(관심사 분리·파일 조직), `plan-gap-interview`(기획 문서의 미결정
  항목), `code-review`(변경분 리뷰), `security-review`(보안 취약점)와는 목적이 다르다
  — 이 스킬은 "설계가 자기 자신과 모순되지 않는가·미래 요구를 버틸 수 있는가"를 감사한다.
- 특정 프로젝트·언어·프레임워크에 종속되지 않는다. 아래 절차는 어떤 저장소에서
  실행해도 그 저장소 기준으로 동작한다.

## 이 스킬이 잡아내려는 실패 패턴

같은 종류의 설계 결함이 코드 리뷰에서 라운드를 거듭하며 반복 발견되는 경우가
전형적인 신호다 — 예: "이 필드는 아직 저장 위치가 없다" → 고치면 → "그 옆 필드도
같은 문제다" → 고치면 → "이 상태 전이는 그 nullable 규칙과 충돌한다". 매번 증상만
고치면 끝나지 않는다. 이 스킬은 그 근본 원인(생명주기·계약·상태 모델링 자체의 결함)을
사후가 아니라 사전에 찾는다.

## 절차

### 1. 설계 표면 스냅샷

무엇이 "설계"에 해당하는지 먼저 식별한다 — ORM/스키마 정의, API 라우터의
요청·응답 타입, 상태값 상수·enum, 이벤트/메시지 스키마, 외부 연동 클라이언트,
ERD·API 계약 문서가 있으면 그것도 포함. 코드가 정본(source of truth)인지 문서가
정본인지 프로젝트 컨벤션을 먼저 확인한다(둘이 어긋나면 그 자체가 첫 번째 발견 사항).

### 2. 체크리스트 검사

각 항목을 실제 코드로 확인하고, 통과/위반 모두 **파일 경로를 근거로** 남긴다.

**① 데이터/스키마 생명주기**
- ID·PK는 언제 발급되는가(DB INSERT 시점 vs 애플리케이션 생성 시점)? 그 시점이
  이 값을 참조하는 다른 스키마(초안/미저장 상태)와 충돌하지 않는가?
- nullable 컬럼·필드마다 "언제 null이고 언제 채워지는가"가 상태값과 정합하는가,
  아니면 nullable로만 선언해두고 불변식이 코드 어디에도 없는가?
- 같은 논리적 엔티티를 가리키는 테이블/컬렉션이 여러 개(예: 여러 번의 재시도·재분석
  row)일 때, "어느 것이 정본인가"를 판정하는 규칙이 존재하는가?
- 서로 다른 보존 기간(retention)을 가진 데이터 사이에 파생·참조 관계가 있다면,
  더 짧게 보존되는 원본이 만료된 뒤에도 더 길게 보존돼야 하는 파생 데이터를
  완전히 재구성할 수 있는가?

**② API·인터페이스 계약**
- 요청/응답 타입이 실제 소비자(화면·다른 서비스)가 필요로 하는 필드를 전부
  포함하는가? 계약과 실사용 사이에 화면이 "2콜"을 해야 채워지는 간극이 있는가?
- 에러 시맨틱이 원인별로 구분되는가(상태코드·에러 타입), 아니면 뭉뚱그려 하나로
  처리되는가? "아직 처리 중"과 "존재하지 않음"과 "실패함"이 같은 응답으로
  뭉개지지 않는가?
- 목록 API에 상한(limit)이 있는가, 무한정 요청을 받는가? 그 상한이 문서화됐는가?
- 재시도해도 안전한가(멱등성)? 멱등이 아니라면 그게 의도적인지 근거가 있는가?

**③ 상태 머신/생명주기**
- 상태값 목록과 허용된 전이가 한 곳에 정의돼 있는가, 코드 곳곳에 문자열로 흩어져
  있는가?
- 동시에 두 요청이 같은 엔티티의 상태를 바꾸려 할 때 무엇이 이기는지 설계돼 있는가?
- "아직 완료되지 않음"과 "완료됐지만 값이 비어있음"을 같은 표현으로 섞어 쓰고
  있지 않은가?

**④ 실패·경계 처리**
- 외부 의존성(다른 서비스·API·큐) 호출이 부분적으로 실패했을 때 무엇이 남는가 —
  일관되지 않은 중간 상태가 관측 가능한가?
- 타임아웃·재시도·폴백 정책이 호출부마다 제각각인가, 공통 정책이 있는가?
- 실패 원인이 로그·에러 타입으로 구분 가능한가, 아니면 문자열 메시지 하나로
  뭉개지는가?

**⑤ 결합도·확장성 트레이드오프**
- 프로젝트 문서에 이미 예고된 다음 단계 요구(예: 로드맵의 다음 Phase)를 지금
  설계가 감당할 수 있는가, 아니면 그 시점에 재작성이 필요한가?
- 재작성이 필요하다면, 그게 지금 시점엔 의도적으로 감수한 트레이드오프로
  문서에 남아 있는가, 아니면 아무도 모르게 방치된 것인가?

**⑥ 설계 일관성**
- 비슷한 문제(여러 상태 머신, 여러 비동기 경계, 여러 외부 연동)가 프로젝트
  전체에서 같은 패턴으로 모델링되는가, 파일마다 제각각인가?
- 제각각이라면 그 차이에 이유가 있는가(문서화됐는가), 아니면 그냥 따로
  만들어져서인가?

**⑦ 신뢰/보안 경계**
- 외부 입력(사용자 자유 입력, 타인이 제어하는 값, 외부 API 응답)이 시스템
  내부 신뢰 영역으로 들어오는 지점이 어디인지 특정 가능한가?
- 그 경계에서 방어(검증·이스케이프·격리)가 설계에 포함돼 있는가, 아니면
  "지금은 우연히 그 경로가 없어서 안전한" 상태에 불과한가(경로가 하나만
  추가돼도 뚫리는 상태)?

### 3. 보고 형식

```markdown
## 견고한 설계 지점
- <제목> (<대상>) — <근거 파일>: <한두 문장, 왜 견고한지 — 어떤 실패를 막는가>

## 설계 결함 또는 위험 지점
- <제목> — <근거 파일>: <구체적으로 무엇이 모순되거나 미정의 상태인가>
  → 실패 시나리오: <이 결함이 실제로 문제가 되는 구체적 입력/상황>
  → 개선 제안: <근본 원인을 없애는 방향 — 증상 땜질이 아니라>

## 판단 유보
- <코드만으로 의도를 알 수 없는 지점 — 팀 확인 필요>
```

- 견고한 지점도 결함만큼 구체적으로 쓴다(왜 이 설계가 특정 실패 클래스를
  구조적으로 막는지).
- 결함은 반드시 "실패 시나리오"(추상적 우려가 아니라 구체적으로 뭐가 잘못되는지)와
  "개선 제안"을 함께 붙인다. 제안은 증상 하나를 고치는 패치가 아니라 근본 원인
  (생명주기·계약·상태 모델 자체)을 겨냥한다.
- 근거 없는 항목은 싣지 않는다 — 모든 항목에 파일 경로가 하나 이상 있어야 한다.

## 하지 말 것

- 코드 수정 (조사만 요청받았다)
- "일반적으로 이렇게 설계하는 게 낫다" 수준의 근거 없는 베스트프랙티스 나열 —
  반드시 이 프로젝트의 구체적 코드·향후 요구사항에 근거해 말한다
- 증상 하나를 지적하고 끝내기 — 같은 근본 원인이 다른 곳에도 반복되는지
  확인한다(오늘 지적 안 한 곳에서 다음 라운드에 같은 문제가 또 나오면 감사가
  실패한 것)
- 스타일/네이밍 지적 (그건 `structure-audit`나 린터의 영역)
- 다른 팀원 설계를 깎아내리는 표현 — 트레이드오프였을 수 있음을 먼저 검토하고
  사실만 중립적으로 기술

## 관련 스킬

- `structure-audit` — 이 프로젝트의 파일·계층 조직 자체를 감사할 땐 그쪽을 쓴다.
- `plan-gap-interview` — 감사 중 "이건 설계 결함이 아니라 애초에 기획에서 결정된
  적이 없는 항목"을 발견하면, 그 항목은 이 스킬로 억지로 결론 내지 말고
  `plan-gap-interview`로 넘겨 인터뷰로 확정한다.
