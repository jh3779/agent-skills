# doc-drift-check — 문서-코드 인용 정합성 검사

> **`$SKILL_DIR`** = 이 `SKILL.md`가 들어 있는 폴더의 절대경로(플러그인 설치본 안). Claude Code는 스킬을 불러올 때 "Base directory for this skill"로 알려 준다. 모르면 `find ~/.claude ~/.codex -path '*/doc-drift-check/SKILL.md'`로 찾아 그 상위 폴더를 쓴다.

## 무엇을 하는가

마크다운 문서 안에서 백틱으로 감싼 `` `path/to/file.py:123` `` 또는
`` `path/to/file.py:123-456` `` 형태의 인용을 전부 찾아, 그 파일이 실제로
존재하고 인용한 줄 수만큼 있는지 확인한다. **결정론적 검사만** 한다(LLM
호출 없음, 임베딩·색인 없음) — Tier 1(구조 확인)만 자동화하고, "그 줄의
내용이 진짜 문서 설명과 일치하는가"(의미 확인)는 사람 또는 에이전트가
직접 읽고 판단한다(아래 "2단계" 참고).

techne의 `docsync` 아이디어를 참고했지만, 여러 저장소가 같은 파일명
(예: 각 서비스의 `main.py`)을 쓰거나 일부 설정 파일이 로컬이 아니라
GitHub에만 있는 실제 환경에 맞춰 직접 구현해 외부 의존성 없이 동작한다.

## 언제 쓰는가

- `.agent/DECISIONS.md`/`HANDOFF.md`처럼 file:line 인용이 많이
  쌓이는 문서를 오래 안 돌아본 뒤 다시 손댈 때
- 개별 프로젝트의 PRD/설계 문서(`docs/PRD-MVP.md` 등)가 실제 코드와 여전히
  맞는지 확인하고 싶을 때
- 대규모 리팩터링 후 관련 문서들이 깨진 인용을 남기지 않았는지 확인할 때

## 절차

1. **대상 문서와 검색 저장소 확정** — 문서가 어느 저장소(들)의 파일을
   인용하는지 파악한다. 흔한 조합:
   - 여러 저장소를 아우르는 운영 문서: 인용되는 저장소마다 `--repo`를
     하나씩 준다(예: `--repo ~/work/api --repo ~/work/web --repo ~/.codex`)
   - 개별 프로젝트 문서: 그 프로젝트 저장소 루트 하나만으로 충분한 경우가
     많음
2. **스크립트 실행**:
   ```bash
   python3 $SKILL_DIR/scripts/check_citations.py \
     <문서.md> --repo <경로1> [--repo <경로2> ...]
   ```
   출력은 세 그룹으로 나뉜다:
   - ✅ **정상**: 파일 존재+줄 수 충분
   - ⚠️ **깨짐**: 파일이 없거나 인용한 줄 수보다 파일이 짧음 — **진짜 드리프트
     후보**
   - ❓ **모호**: 같은 파일명이 여러 저장소에 있어 어느 걸 가리키는지 도구가
     자동으로 못 정함(예: `main.py`가 여러 서비스 저장소 각각에 있음) — 도구가
     조용히 추측하지 않고 사람/에이전트 판단에 넘긴 것
3. **"깨짐" 결과를 그대로 믿지 말고 문맥 확인** — 아래 "알려진 오탐 패턴"에
   해당하는지 먼저 걸러낸다.
4. **2단계(선택, 의미 확인)** — "깨짐"·"모호" 항목 중 중요한 것만 골라
   실제로 열어서(`Read` 도구) 그 인용 주변 문서 설명이 지금도 코드 동작과
   맞는지 직접 읽고 판단한다. 이 단계는 자동화하지 않는다 — 정확한 판단이
   필요한 부분이라 LLM(에이전트) 판단으로 남겨둔다.
5. **결과 보고** — structure-audit/architecture-audit과 같은 형식(근거
   파일:줄 인용, 판단 유보 항목 구분)으로 정리해 사용자에게 전달한다.

## 알려진 오탐 패턴 (⚠️ "깨짐"으로 나와도 실제 드리프트가 아닐 수 있음)

- **서드파티 라이브러리 참조**: `abc.py`, `tasks/__init__.py`처럼
  discord.py 등 설치된 패키지 내부 파일을 근거로 인용한 경우 — 이 도구는
  `.venv`/`node_modules`를 검색 대상에서 제외하므로 항상 "못 찾음"으로
  나온다. 실제 드리프트가 아니라 도구의 스코프 밖.
- **GitHub에만 저장되는 파일**: 봇이 API로 읽어 오는 `projects.yml`처럼 로컬
  디스크가 아니라 `gh_get_file()`로 GitHub 레포에서 직접 읽어오는 설정
  파일은 로컬 파일시스템 검색으로 절대 못 찾는다 — 이건 도구의 한계이지
  드리프트 신호가 아니다(문서에 "GitHub 저장 파일"이라는 표시가 있는지
  확인).
- **일반 패턴 설명**: "각 프로젝트의 `PRODUCT.md`/`DESIGN.md`를 확인한다"
  처럼 특정 파일이 아니라 "이런 이름의 파일이 있으면"이라는 일반 규칙을
  설명하는 문장 — 실제로 그 이름의 파일이 지금 저장소에 있어야 한다는
  뜻이 아니다.
- **데이터 디렉터리**: `~/data/<건별>/config.yaml`처럼 코드
  저장소가 아니라 건별 데이터 디렉터리에 있는 파일 — 검색 대상 `--repo`
  목록에 그 디렉터리를 추가하지 않으면 항상 "못 찾음"으로 나온다.

## DECISIONS.md류 "append-only 역사 기록" 문서는 다르게 판단할 것

`.agent/DECISIONS.md`처럼 `handoff` 스킬 관례로 "기존 항목은
절대 수정하지 않는다"는 원칙이 적용되는 문서에서는, "깨짐"으로 나온
인용이 **그 항목을 작성한 시점엔 정확했을 수 있다** — 이후 파일이
옮겨지거나 이름이 바뀐 것뿐이다. 이런 경우는 "드리프트를 고쳐야 한다"가
아니라 "그 결정이 내려진 시점의 기록이니 그대로 둔다"가 맞는 판단이다.
**PRD/README/스킬 문서처럼 "지금 상태를 설명하는" 문서**(append-only가
아닌 문서)에서 나온 "깨짐"만 실제로 고쳐야 할 드리프트로 취급한다. 헷갈리면
그 문서가 시간 순으로 쌓이는 로그 형식인지, 아니면 "지금은 이렇다"를
서술하는 형식인지 먼저 확인한다.

## 실제 검증 사례 (2026-09-14, 운영 저장소의 `.agent/DECISIONS.md`)

첫 실행에서 "깨짐" 1건 — 한 결정 항목이 인용한 PRD 파일이 지금은 그 위치에
없음. 확인해보니 **드리프트가 아니라 정상**이었다 — 그 항목은 PRD가 원래
위치에 있던 시점의 기록이고, 이후 다른 폴더로 옮긴 사실은 같은 문서의 다른
항목에 이미 기록돼 있었다(=위 "append-only 역사 기록" 규칙 그대로).
나머지 "깨짐" 결과는 전부 "알려진 오탐 패턴"에 해당했다(서드파티
라이브러리 2건, GitHub 저장 파일 2건, 일반 패턴 설명 1건, 데이터
디렉터리 1건) — 즉 이번 첫 실행에서는 **진짜 고쳐야 할 드리프트가
0건**으로 확인됐다(도구가 정상 작동해 오탐을 스스로 잘 걸러냈다는 뜻).

## 하지 말 것

- "모호" 결과를 임의로 하나 골라 "이게 맞겠지"로 단정하지 않는다 — 후보
  전부를 사용자에게 보여주고 판단을 넘긴다.
- "깨짐" 결과를 위 오탐 패턴 확인 없이 그대로 "드리프트 N건 발견"으로
  보고하지 않는다 — 반드시 맥락을 확인한 뒤 진짜 드리프트만 추린다.
- 이 도구는 **구조 확인(파일·줄 존재)만** 한다 — "이 문장이 지금도 사실인가"
  같은 의미 검증은 못 한다고 명시하지 않고 넘어가지 않는다.
