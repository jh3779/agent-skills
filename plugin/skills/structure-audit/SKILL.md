# structure-audit — 관심사 분리·파일 조직 감사

## 목적과 범위

프로젝트가 **관심사를 얼마나 잘 나눴고, 파일을 얼마나 일관되게 조직했는지**를
근거(파일 경로·코드 인용)와 함께 평가한다.

- 코드를 **수정하지 않는다** — 조사와 보고만. 수정은 사용자가 명시적으로 요청할 때만 별도로.
- 죽은 코드 제거(`refactor-cleaner`), 변경분 리뷰(`code-review`), 온보딩 문서 생성
  (`codebase-onboarding`)과는 목적이 다르다 — 이 스킬은 "구조 품질의 평가"다.
- 특정 프로젝트·언어에 종속되지 않는다. 아래 절차는 어떤 저장소에서 실행해도
  그 저장소 기준으로 동작한다.

## 절차

### 1. 구조 스냅샷

```bash
# 소스 파일 트리 (언어에 맞게 확장자 조정)
find <src-dir> -type f \( -name "*.py" -o -name "*.ts" -o -name "*.go" \) | sort
```

디렉터리 이름에서 의도된 계층 구조를 추정한다(예: `routers/`+`services/`+`schemas/`,
`controllers/`+`models/`, `cmd/`+`internal/`). 프로젝트 문서(README, CLAUDE.md,
docs/architecture 류)가 선언한 구조가 있으면 그것을 기준으로 삼는다 —
**문서가 말하는 구조와 실제 파일 배치의 불일치 자체가 첫 번째 발견 사항**이다.

### 2. 체크리스트 검사

각 항목을 실제 코드로 확인하고, 통과/위반 모두 **파일 경로를 근거로** 남긴다.

**① 계층 분리**
- 진입점(main/app)은 조립만 하는가, 로직이 섞여 있는가?
- HTTP/CLI 계층(라우터)이 도메인 로직을 직접 수행하지 않고 서비스에 위임하는가?
- 서비스 계층이 프레임워크 객체(Request 등)를 직접 받는가, 아니면 필요한 값·콜러블만
  주입받는가? (후자가 더 나은 분리 — 프레임워크 의존이 안쪽으로 새지 않음)

**② 도메인별 파일 대칭성**
- 같은 성격의 디렉터리들(routers/schemas/services 등)이 같은 도메인명 파일로
  나란히 있는가? 한 도메인만 빠져 있으면 그 이유가 정당한가(불필요해서인가, 누락인가)?
- 새 도메인을 추가할 때 "어디에 뭘 만들지"가 구조만 보고 자명한가?

**③ import 방향**
```bash
# 예: 하위 계층이 상위 계층을 역방향 import하는지 (파이썬 예시)
grep -rn "from app.routers\|import app.routers" <src-dir> --include="*.py" | grep -v "app/main"
```
- 도메인 로직·도구 계층이 라우터/HTTP 계층을 import하면 역방향 의존 — 위반.
- 진입점 외에 라우터를 import하는 곳이 있으면 조사.

**④ 공유 로직의 소비자별 어댑터**
- 하나의 핵심 로직을 여러 소비자(HTTP, LLM 도구, CLI 등)가 쓸 때, 로직이 복사돼
  있는가 아니면 공유하되 어댑터(예외 번역, 응답 포맷)만 소비자별로 나뉘어 있는가?
- 예외가 소비자에 맞게 번역되는가(HTTP엔 상태코드, LLM엔 읽을 수 있는 메시지)?

**⑤ DI·설정 판단의 집중도**
- 인스턴스 생성/캐싱/공유 판단이 한 곳(dependencies, container 류)에 모여 있는가,
  흩어져 있는가?
- 같은 패턴인데 어떤 것은 캐싱하고 어떤 것은 안 한다면, 그 **이유가 주석·문서로**
  남아 있는가? (이유 없는 비일관성은 위반, 이유 있는 비일관성은 잘한 지점)

**⑥ 횡단 관심사(cross-cutting concerns) 분리**
- 로깅/관측: 비즈니스 코드에 전송·수집 로직이 섞여 있는가, 표준 로깅·미들웨어로
  옆에서 가로채는가?
- 보안 검증(경로 화이트리스트, 입력 검증): 그 검증이 필요한 계층에만 있는가,
  아니면 아무 데나 흩어져 있는가?
- 예외 타입: 실패 종류가 타입으로 구분되는가, 문자열로 뭉개지는가?

**⑦ 프론트엔드(있는 경우)**
- 백엔드와 같은 분리 원칙이 적용됐는가(도메인별 함수 분리, 공용 유틸 추출)?
- 서버 계약(이벤트 포맷 등)이 바뀌었을 때 깨지는 지점이 한 곳에 모여 있는가?

**⑧ 계약의 일관성**
- 같은 성격의 인터페이스(예: SSE 이벤트, 에러 응답 포맷)가 도메인마다 제각각인가
  통일돼 있는가? 제각각이라면 흡수 계층(범용 파서 등)이 있는가?

### 3. 보고 형식

```markdown
## 잘 구분한 지점
- <제목> (<담당/영역>) — <근거 파일>: <한두 문장 설명, 왜 잘한 것인지>

## 위반 또는 아쉬운 지점
- <제목> — <근거 파일>: <무엇이 섞여 있는지 / 무엇이 비대칭인지>
  → 개선 제안: <구체적으로 어디를 어떻게>

## 판단 유보
- <코드만으로 의도를 알 수 없는 지점 — 팀 확인 필요>
```

- 잘한 지점도 위반만큼 구체적으로 쓴다(발표·회고 자료로 재사용 가능하도록).
- 위반은 반드시 개선 제안을 붙이되, 수정은 하지 않는다.
- 근거 없는 항목은 싣지 않는다 — 모든 항목에 파일 경로가 하나 이상 있어야 한다.

## 하지 말 것

- 코드 수정·파일 이동 (조사만 요청받았다)
- 근거 없이 "일반적으로 좋다/나쁘다" 수준의 평가
- 컨벤션 위반과 "이유가 문서화된 의도적 예외"를 구분하지 않고 싸잡아 지적
- 다른 팀원 코드를 깎아내리는 표현 — 상황 차이(그 파트엔 그 분리가 필요 없었을
  수 있음)를 먼저 검토하고, 사실만 중립적으로 기술
