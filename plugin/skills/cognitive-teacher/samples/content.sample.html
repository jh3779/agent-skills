주문 한 건이 구워지기까지 주제 모드 샘플 · 가상의 프로젝트 예시입니다

학습 목표
1

배경worker 모드 이전에는 어떻게 돌아갔나

초기의 cakeshop은 프로세스를 직접 띄워 그날의 주문을 한 번에 굽고 종료하는 구조였습니다. 실행 시점은 전적으로 CronJob 스케줄에 묶여 있었고, 손님이 앱에서 "지금 바로 구워줘"라고 요청할 방법이 없었습니다.

이 부분을 이미 알고 있다면 접어두세요 — 직접 실행 모드의 한계 (2문단)

직접 실행 모드에서는 급한 주문이 들어와도 사람이 수동으로 굽기 파이프라인을 돌려야 했습니다. API 서버는 주문을 받아도 굽기 프로세스에 전달할 통로가 없었기 때문입니다.

그래서 도입된 것이 주문을 DB 테이블에 쌓고, 상시 구동 worker가 그걸 집어가는 큐 구조입니다. API와 worker는 서로를 직접 호출하지 않고 bake_orders 테이블만 공유합니다.

이 문서가 다루는 것은 그 큐 구조, 즉 CAKESHOP_RUN_MODE=worker가 기본이 된 현재의 파이프라인입니다.

2

직관이 구조의 본질 한 줄

worker 모드의 본질은 "주문하는 쪽"과 "굽는 쪽"의 분리입니다. 매장에 비유하면 카운터(API)는 주문서를 주문대에 꽂기만 하고, 주방(worker)은 자기 리듬으로 주문대를 확인하며 주문서를 하나씩 집어갑니다. 카운터가 주방에 직접 소리치지 않으므로, 주방이 바쁘든 재시작 중이든 주문은 유실되지 않습니다.

정기 주문(매일 아침 식빵 50개)도 같은 주문대를 씁니다 — CronJob은 enqueue 모드로 "주문서를 꽂는 역할"만 하고, 굽는 일은 언제나 worker의 몫입니다.
  • API는 bake_orders에 행을 넣기만 한다
  • worker는 이 테이블을 폴링해서 주문을 집어간다 (claim)
  • 정기 주문 = worker 내장 스케줄러 + enqueue 모드 CronJob

4

코드 읽기claim은 왜 이렇게 생겼나

두 worker가 동시에 같은 주문을 집으면 같은 케이크가 두 번 구워집니다. 이를 막는 것이 claim 쿼리이고, 서사의 순서상 가장 먼저 읽어야 할 코드는 잠금 선점 부분입니다. (아래는 가상의 예시 diff입니다)

cakeshop/worker/claim.py
@@ -41,6 +41,9 @@ def claim_next_order(session):
     stmt = (
         select(BakeOrder)
         .where(BakeOrder.status == "queued")
+        .order_by(BakeOrder.created_at)
+        .with_for_update(skip_locked=True)
-        .limit(1)
+        .limit(1)  # 잠긴 행은 건너뛰고 첫 주문만
     )

skip_locked가 이 구조의 안전핀입니다. 다른 worker가 이미 잡은 행은 기다리지 않고 건너뛰므로, worker 수를 늘려도 같은 주문이 중복으로 구워지지 않습니다.
