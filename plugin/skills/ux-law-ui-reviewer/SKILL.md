# UX Law UI Reviewer

사용자가 준 화면(스크린샷, 시안, URL, HTML/CSS/JS, React·Vue 코드, 화면 설명, 사용자 흐름, 와이어프레임, 게임 HUD·메뉴, 기존 UX 리뷰 문서)을 **실제로 검토**하고, 사용자가 핵심 정보와 다음 행동을 쉽게 찾는지 진단한 뒤 UX 법칙을 근거로 **구체적인 수정안**을 낸다. 법칙 설명서가 아니라 실무용 리뷰 도구다. 결과는 날짜별 HTML 파일로 저장해 기록을 남긴다(3-1).

## 언제 쓰나

다음과 같은 요청이면 이 스킬을 쓴다.

- "이 UI를 UX 관점에서 검토해줘", "스크린샷/시안 평가해줘"
- "화면이 왜 복잡한지 분석해줘", "정보 구조 정리해줘"
- "버튼·메뉴 배치 개선해줘", "다음 행동을 쉽게 찾는지 봐줘"
- "UX 법칙 적용해서 리디자인해줘"
- "HTML/CSS·프론트엔드 화면 검토해줘"
- "게임 HUD 가독성·조작성 봐줘", "모바일 터치 동선 확인해줘"

UX 법칙의 정의만 묻는 질문(“힉의 법칙이 뭐야?”)은 이 스킬 없이 짧게 답한다.

## 관련 스킬과 역할 분담

이 스킬은 **"사용자가 핵심 행동을 쉽게 찾고 실수 없이 수행하는가"** 를 다섯 법칙으로 진단하고 기록하는 데 특화돼 있다. 같은 컴퓨터의 `design-review`(구 impeccable)와 일부 겹치므로 아래처럼 나눈다.

| 요청 성격 | 쓰는 스킬 | 이유 |
|---|---|---|
| 법칙 근거의 UX 진단, 터치 영역·동선, 게임 HUD·모바일 터치, 날짜별 HTML 기록 | **ux-law-ui-reviewer** (이 스킬) | 법칙→문제→수정 근거 사슬, 수치 출처 표기, 게임·터치 모드, 기록 파일은 이쪽에만 있다 |
| 디자인 비평(Nielsen 10 휴리스틱 점수·페르소나·감지기 스캔), 기술 감사, polish·layout·typeset 등 개선 실행 | `design-review` | 미감·타이포·색·모션·성능·i18n과 실제 수정 커맨드는 이쪽이 맡는다 |
| 새 화면·랜딩 제작, 와이어프레임 | `design-generation` | 생성 단계. 만든 뒤 검증에 이 스킬을 쓴다 |

- 둘 다 해당하면(예: "종합 디자인 검토") **이 스킬을 먼저** 돌린다(빠르고 범위가 좁다). 이어서 `design-review critique`를 돌리고, 같은 문제는 한 건으로 합치되 법칙 태그는 남긴다. 다른 스킬의 결과를 이 스킬의 HTML 기록에 섞어 넣지 않는다.
- 심각도 대응(참고): Critical≈P0, High≈P1, Medium≈P2, Low≈P3, Suggestion=백로그. 이 스킬의 리포트에는 이 스킬의 5단계 이름만 쓴다.
- 수정을 **실행**할 단계라면 법칙별로 아래 커맨드를 제안한다(실행 여부는 사용자가 정한다).

| 지적한 법칙 | 이어서 쓸 `design-review` 커맨드 |
|---|---|
| 힉 (선택지·정보 과다) | `distill`(덜어내기), `onboard`(단계별 공개) |
| 피츠 (크기·거리·오조작) | `adapt`(기기별 터치 영역), `layout` |
| 제이콥 (관습 이탈·아이콘 모호) | `clarify`(라벨·문구), `harden`(상태·오류) |
| 근접성 (간격·그룹) | `layout` |
| 폰 레스토프 (강조 과다·부족) | `quieter`(강조 줄이기), `bolder`(핵심 키우기), `colorize` |

## 0. 입력 처리

자료가 부족해도 **먼저 확인 가능한 범위에서 분석**한다. 결과가 크게 달라지는 정보만 마지막에 한 번 묻는다(예: 주 사용 기기, 화면의 핵심 목적이 불분명할 때). 사소한 정보는 합리적으로 가정하고 "가정:"으로 명시한다.

| 입력 | 처리 방법 | 주의 |
|---|---|---|
| 스크린샷·시안·와이어프레임 | 이미지를 직접 본다. 화면을 영역(헤더/본문/사이드/하단 등)으로 나눠 요소 목록을 먼저 만든다. | 픽셀 크기는 해상도·배율을 모르면 **추정**으로 표기. 보이는 크기와 실제 클릭 영역을 구분할 수 없다고 명시. |
| URL | 브라우저 도구가 있으면 페이지를 열어 데스크톱/모바일 폭에서 확인하고, DOM에서 실제 크기·대비를 측정한다. 없으면 페이지 텍스트로 구조만 보고 시각 판단은 "판단 자료 부족". | 로그인 뒤 화면은 볼 수 없음을 밝힌다. |
| HTML/CSS/JS, React·Vue 등 코드 | 렌더 구조를 머릿속(가능하면 실제 렌더)으로 재구성한다. 문제마다 **파일명·컴포넌트·선택자·줄 번호**를 근거로 단다. 패딩·min-height·gap·색상값으로 터치 영역과 대비를 계산한다. | 반응형 분기(media query), 조건부 렌더링 때문에 화면이 여러 상태일 수 있다. |
| 화면 설명·사용자 흐름 | 서술을 요소 목록과 단계표로 바꿔 놓고 분석한다. | 시각 강조·간격은 대부분 "판단 자료 부족". |
| 게임 HUD·메뉴 | 아래 "게임 UI 모드"를 함께 적용한다. | 장르·입력장치(패드/키마/터치)에 따라 기준이 달라진다. |
| 기존 UX 리뷰 문서 | 지적 사항을 다섯 법칙에 재분류하고, 근거가 약하거나 취향인 지적을 가려낸다. | 원문 결론을 그대로 믿지 않는다. |

## 1. 분석 절차

1. **목적·사용자 파악**: 이 화면은 무엇을 위해 있고 누가 쓰는가. 불명확하면 가장 그럴듯한 해석을 가정으로 적는다.
2. **핵심 행동 정의**: 진입 직후 사용자가 해야 할 행동 1~2개(예: "결제하기", "적 위치 확인 후 회피").
3. **정보 계층·시각 우선순위**: 눈이 처음 가는 곳 → 두 번째 → 세 번째를 적고, 이것이 핵심 행동 순서와 맞는지 본다.
4. **다섯 법칙별 점검**: 아래 부록 A 체크리스트 사용.
5. **취향 vs 사용성 구분**: "나라면 파란색"은 취향. 행동 지연·오작동·누락 같은 **사용자 결과**로 설명되지 않으면 문제로 올리지 않는다(필요하면 Suggestion).
6. **심각도·우선순위 결정**: 아래 기준.
7. **최소 수정안 먼저**: 현재 구조를 유지한 채 바꿀 수 있는 것.
8. **확장 개선안은 별도로**: 구조 재설계가 필요할 때만.
9. **코드 근거**: 코드가 있으면 위치를 반드시 표기.
10. **개선 효과 설명**: 고친 뒤 사용자가 무엇을 더 쉽게 하게 되는지.

## 2. 심각도 기준

- **Critical**: 주요 작업을 완료하기 어렵거나 중대한 오작동(삭제·결제·전송 오클릭 등) 가능성
- **High**: 핵심 행동을 찾거나 수행하는 데 큰 혼란
- **Medium**: 효율·가독성·일관성이 눈에 띄게 떨어짐
- **Low**: 개선하면 좋지만 핵심 사용엔 영향 작음
- **Suggestion**: 선택적 발전 아이디어

문제는 **심각도 높은 순**으로 정렬한다. 같은 심각도 안에서는 핵심 행동에 가까운 것부터.

## 3. 출력 템플릿

아래 순서와 제목을 그대로 쓴다. 문제 수는 실제로 발견된 만큼만(억지로 채우지 않음). 사용자 언어로 작성한다.
이 7개 섹션 구조는 **HTML 기록 파일(기본 산출물, 3-1 참고)**의 내용 구조이기도 하다. 사용자가 "채팅으로만", "파일 없이"라고 하면 아래 마크다운으로 채팅에 직접 답한다.

```markdown
## 1. 한줄 평가
<화면의 가장 중요한 UX 상태를 한 문장으로>

## 2. 핵심 행동
- **핵심 행동**: …
- **현재 발견 가능성**: 높음/보통/낮음 — <이유 한 줄>
- **방해 요소**: …
- (가정: … ← 있을 때만)

## 3. 주요 문제
### [심각도] 문제 제목
- **적용 법칙**: <법칙명 또는 "법칙 외: 접근성" 등>
- **위치/요소**: <화면 영역, 또는 파일:줄·컴포넌트·선택자>
- **왜 문제인가**: …
- **사용자 영향**: …
- **수정 방법**: <대상·위치·방법을 구체적으로. 수치는 근거 표기>

(반복)

## 4. UX 법칙별 점검표
| 법칙 | 평가 | 근거 |
|---|---|---|
| 힉의 법칙 | 양호/개선 필요/문제 있음/판단 자료 부족 | 1~2문장 |
| 피츠의 법칙 | … | … |
| 제이콥의 법칙 | … | … |
| 근접성의 법칙 | … | … |
| 폰 레스토프 효과 | … | … |

**잘 된 점**: <실제로 효과 있는 설계 1~3개만, 형식적 칭찬 금지>

## 5. 우선순위별 개선안
**이번 버전에 꼭 필요한 것**
- …
**다음 버전에서 개선해도 되는 것**
- …
**현재는 제외하는 것이 좋은 것**
- … (제외 이유: 비용 대비 효과, 범위 초과 등)

## 6. 적용 예시
<입력에 맞는 형식 하나 이상: 전후 구조 비교 / ASCII 와이어프레임 / 컴포넌트 재배치안 / 버튼·문구 수정안 / 코드 diff / HUD 배치도>

## 7. 최종 체크리스트
- [ ] … (5~10개, 사용자가 직접 확인 가능한 관찰 가능한 기준으로)
```

입력이 아주 작을 때(버튼 하나, 짧은 설명)는 섹션 6을 간단히 하되 섹션 순서는 유지한다.

### 범위 통제
- 개선안을 한꺼번에 다 구현하도록 유도하지 않는다. "이번 버전" 항목은 현재 목적과 완료 기준을 달성하는 데 필요한 것만 넣는다(보통 3~5개).
- 전면 재설계는 최소 수정으로 해결이 안 될 때만 "확장 개선안"으로 따로 제시한다.

## 3-1. HTML 기록 파일 (기본 산출물)

리뷰 결과는 **HTML 파일로 저장해 기록을 남기는 것이 기본**이다. 웹 페이지(공유 링크)로 게시하지 않는다. 사용자가 공유 링크를 명시적으로 원할 때만 게시한다.

**저장 위치**
- 검토 대상이 프로젝트 안에 있으면(Claude Code·Codex 등 파일 시스템 접근 환경): 그 프로젝트 루트의 `ux-reviews/`. 폴더가 없으면 만든다. 프로젝트가 불분명하면 작업 디렉터리 기준으로 하되 경로를 알린다.
- 컴퓨터 폴더가 연결돼 있으면: 검토 대상 프로젝트 폴더(또는 연결된 첫 폴더) 안의 `ux-reviews/`.
- 연결된 폴더가 없으면(파일 시스템 접근이 없는 대화형 환경 등): 작업 공간의 출력 폴더 `ux-reviews/`에 만들고 파일로 전달한다. 컴퓨터 폴더를 연결하면 그곳에 쌓을 수 있다고 한 줄 안내한다.
- `design-review`의 `critique`가 쓰는 `.impeccable/critique/`와는 별개 저장소다. 서로 덮어쓰거나 합치지 않는다.

**파일 규칙**
- 파일명: `YYYY-MM-DD_<화면-slug>.html` (slug는 영문 소문자·숫자·하이픈, 예: `2026-10-04_checkout-mobile.html`).
- 같은 이름이 있으면 덮어쓰지 말고 `_2`, `_3`을 붙인다. 이전 리뷰는 절대 수정·삭제하지 않는다.
- 같은 화면의 재검토라면 헤더 meta에 `<span>이전 리뷰 <b><a href="이전파일.html">YYYY-MM-DD</a></b></span>`를 추가하고, 한줄 평가 아래에 이전 대비 해결된 문제·남은 문제를 한 줄로 적는다.
- `ux-reviews/index.html`(기록 인덱스)을 갱신한다. 없으면 `templates/review-index.html`(부록 E)을 복사해 만들고, `<!-- ROWS (최신이 위) -->` 주석 바로 아래에 새 `<tr>` 한 줄을 넣는다. 기존 줄은 건드리지 않는다.

**채우는 법** (`templates/review-report.html` = 부록 D. 저장 직전에 이 파일을 읽어 복사한다)
1. 템플릿 전체를 복사하고 맨 위 작성 안내 주석을 `<!-- ux-law-ui-reviewer v1 · 날짜 · 화면명 -->` 한 줄로 바꾼다.
2. `{{…}}` 자리표시자를 모두 실제 내용으로 바꾼다. 저장 전 `{{`가 남지 않았는지 확인한다.
3. `REPEAT:이름` ~ `/REPEAT` 주석 사이 블록은 항목 수만큼 복제하고, 쓰지 않는 블록(예: 6번의 문구 수정표)은 통째로 지운다.
4. 문제 카드는 심각도 높은 순. `data-severity`(critical|high|medium|low|suggestion)와 `data-laws`(hick fitts jakob proximity restorff other, 공백 구분)를 정확히 넣는다. 배지 문구와 `sev` 클래스도 맞춘다.
5. 점검표 상태 클래스: `st-good` 양호 / `st-improve` 개선 필요 / `st-bad` 문제 있음 / `st-na` 판단 자료 부족.
6. 코드·와이어프레임 안의 `<` `>` `&`는 `&lt;` `&gt;` `&amp;`로 이스케이프한다. 주석 안에 `-->`를 쓰지 않는다.
7. diff는 `<pre class="diff">` 안에서 줄마다 `<span class="add|del|ctx">`로 감싼다.
8. 심각도 개수, 필터 칩, 체크리스트 진행률은 템플릿 스크립트가 자동 계산하므로 직접 쓰지 않는다.
9. 셸이 있으면 저장 뒤 한 번 확인한다: `{{` 잔존 여부(1단계 주석 교체 뒤에 검사), 문제 카드 수와 인덱스의 C/H/M 개수가 일치하는지.

**채팅 답변**: 보고서 전문을 채팅에 다시 붙이지 않는다. 한줄 평가, Critical·High 문제 제목, 저장된 파일 경로(폴더 이름과 파일명)만 짧게 알린다.

## 4. 리뷰 원칙

- 개인 취향을 UX 법칙처럼 단정하지 않는다.
- 모든 문제에 법칙을 억지로 연결하지 않는다. 다섯 법칙 밖의 문제는 "법칙 외: …"로 표기하고, 이름은 아래 분류 중 하나를 쓴다(Nielsen 휴리스틱과 대응, 리포트마다 이름이 달라지지 않게).
  - `접근성`(대비·키보드·스크린 리더·터치 영역 하한) · `피드백·상태`(Nielsen 1) · `문구·용어`(Nielsen 2·10) · `일관성`(Nielsen 4) · `오류 예방·복구`(Nielsen 5·9)
  - 법칙 외 문제가 많아 보이면 `design-review critique`를 이어서 쓰자고 한 줄 제안한다(점수화된 휴리스틱 평가는 그쪽이 맡는다).
- 디자인이 남다르다는 이유만으로 제이콥의 법칙 위반이라 하지 않는다. **사용자가 기존 관습대로 행동했을 때 실패하는지**가 기준.
- 시각적으로 눈에 띄는 것(크기·색)과 실제 클릭·터치 가능한 영역(hit area)을 구분한다.
- 화면 하나로 전체 흐름을 확정하지 않는다. 앞뒤 화면에 대한 추정은 추정이라고 쓴다.
- 접근성과 일반 UX를 구분하되, 색 대비·키보드 이동·스크린 리더 라벨·터치 영역처럼 명백한 문제가 보이면 함께 알린다.
- 수치를 제시하면 출처를 붙인다(부록 B). 출처 없는 경험칙은 "경험칙"이라고 쓴다.
- 근거가 부족하면 "추정"이라고 명시한다.
- "더 깔끔하게", "직관적으로" 같은 말 대신 **무엇을, 어디서, 어떻게** 바꿀지 쓴다.
- 장점은 짚되 짧게. 문제 발견을 가리지 않게 한다.

## 5. 모드별 추가 지침

### 스크린샷·시안 모드
- 시작 전에 화면을 영역별로 나눠 요소를 열거한다(내부 작업, 출력에는 필요한 만큼만).
- 이미지 해상도로 실제 크기를 환산할 수 없으면 "상대 크기"로 비교한다(예: "주 CTA가 옆 보조 버튼과 같은 높이·같은 무게").
- 그림자·색만으로 클릭 가능 여부를 알 수 없는 요소는 "어포던스 불명확"으로 표시.

### 코드 리뷰 모드
- 근거는 `파일:줄` 또는 컴포넌트·선택자로 단다.
- 터치 영역 = 콘텐츠 + padding (+ border). `min-height`, `line-height`, `gap`, 인접 요소와의 거리를 계산해 보여준다.
- 아이콘 전용 버튼에 `aria-label`/텍스트가 없는지, `div onClick`처럼 키보드 접근이 안 되는 요소가 있는지, `outline: none`으로 포커스 표시를 지웠는지 확인한다.
- 색상값이 코드에 있으면 대비비를 어림하지 말고 WCAG 상대 휘도 공식으로 계산한다(셸이 있으면 짧은 스크립트로). 배경색이 코드에 없으면 가정한 배경을 밝힌다.
- 강조 색(`--primary`, `btn-primary` 등)이 몇 곳에 쓰이는지 세어 폰 레스토프 판단 근거로 쓴다.
- 수정 예시는 diff 또는 바뀐 부분만 담은 짧은 코드로 준다. 기존 코드 스타일(Tailwind/CSS Modules/styled-components 등)을 따른다.

### 게임 UI 모드
- 장르와 입력장치를 먼저 정한다(모르면 가정 명시).
- **힉**: 전투 중 동시에 판단해야 하는 정보량, 스킬바·인벤토리 선택지 수, 메뉴 깊이.
- **피츠**: 패드에선 커서 이동 거리 대신 **입력 횟수·버튼 매핑**, 키마에선 화면 중앙(조준점)↔HUD 요소 시선 이동 거리, 터치에선 엄지 도달 범위와 가상 패드 겹침.
- **제이콥**: 장르 관례(체력=좌상단/좌하단, 미니맵=우상단, 확인/취소 버튼 매핑의 플랫폼 관례 등). 관례와 달라도 튜토리얼·일관성으로 학습되면 문제 아님.
- **근접성**: 체력·자원·상태이상처럼 함께 보는 정보의 묶음, 쿨다운 표시와 해당 스킬의 거리.
- **폰 레스토프**: 위험 신호(저체력, 적 공격 예고)가 장식 이펙트에 묻히지 않는지, 강조 색이 위험/보상 등 의미별로 일관된지.
- 추가로 확인: 화면 중앙 시야 가림, 화면 흔들림·이펙트 위 텍스트 대비, 자막·글자 크기, 색약 대응(색 외 형태·아이콘 병기).

### 모바일 터치 모드
- 주요 반복 행동이 한 손 엄지로 닿는 하단 영역에 있는지, 위험 행동(삭제·나가기)이 주 CTA 바로 옆에 붙어 있지 않은지 본다.
- 엄지 도달 영역은 기기 크기·잡는 방식에 따라 다르므로 **경험칙**으로 표기한다.

## 부록 A. 법칙별 체크리스트

### A1. 힉의 법칙 (Hick's Law)
선택지·정보가 많을수록 결정 시간이 늘어난다. (선택지가 익숙하고 정렬된 목록이면 영향이 줄어든다는 점도 고려)
- [ ] 한 화면의 동시 선택지가 과도한가(주요 행동 후보를 세어본다)
- [ ] 주요 행동과 보조 행동이 구분되는가
- [ ] 메뉴·필터·설정이 의미 단위로 묶여 있는가
- [ ] 지금 필요 없는 정보·옵션이 함께 노출되는가
- [ ] 단계별 공개, 기본값·추천값을 쓸 수 있는가

개선: 선택지 축소, 카테고리화, 단계별 공개(더보기·고급 설정·스텝), 추천값/기본값, 주요·부가 행동 분리(오버플로 메뉴 등)

### A2. 피츠의 법칙 (Fitts's Law)
목표까지의 거리가 멀고 크기가 작을수록 도달 시간과 오류가 늘어난다.
- [ ] 버튼·터치 영역이 충분한가(부록 B 기준)
- [ ] 자주 쓰는 기능이 가까운가(이전 동작 위치 기준)
- [ ] 인접 버튼 간격이 오작동을 막을 만큼인가
- [ ] 모바일에서 엄지로 조작하기 쉬운가
- [ ] 위험 행동이 주요 버튼과 너무 가까운가

개선: hit area 확대(시각 크기는 유지하고 padding만 늘리는 방법 포함), 주 버튼 위치 조정, 관련 컨트롤 근접 배치, 위험 행동 분리·확인 단계, 동선 단축

### A3. 제이콥의 법칙 (Jakob's Law)
사용자는 다른 서비스에서 익힌 방식대로 행동한다.
- [ ] 일반적인 UI 관습을 따르는가(로고=홈, 검색 위치, 장바구니 아이콘 등)
- [ ] 아이콘·버튼 의미를 예상할 수 있는가(라벨 없는 모호한 아이콘)
- [ ] 익숙한 기능을 불필요하게 새 방식으로 만들었는가
- [ ] 화면 간 내비게이션 규칙이 일관적인가
- [ ] 플랫폼 관례(iOS/Android/웹/콘솔)와 충돌하는가

개선: 익숙한 패턴 사용, 아이콘+텍스트 라벨, 내비게이션 통일, 플랫폼 표준 준수, 새 방식이 꼭 필요하면 온보딩·힌트·즉각 피드백

### A4. 근접성의 법칙 (Law of Proximity)
가까운 요소는 관련 있는 것으로 인식된다.
- [ ] 관련 정보가 시각적으로 묶여 있는가
- [ ] 무관한 요소가 너무 가까운가
- [ ] 섹션 간 간격 > 섹션 내부 간격이 명확한가
- [ ] 라벨·설명·입력창·오류 메시지의 관계가 분명한가(라벨이 위 입력창과 아래 입력창 사이 중간에 떠 있지 않은가)
- [ ] 카드·목록 경계가 구분되는가

개선: 관련 요소 간격 축소, 섹션 간격 확대, 그룹 컨테이너·배경, 간격 스케일 통일(예: 4/8/16/24/32), 정렬·계층 정리

### A5. 폰 레스토프 효과 (Von Restorff Effect)
여러 요소 중 다른 하나가 가장 잘 주목·기억된다.
- [ ] 가장 중요한 요소를 즉시 알 수 있는가(3초 응시 테스트)
- [ ] 동시에 강조된 요소가 너무 많은가
- [ ] 강조 색이 일관된 의미로 쓰이는가
- [ ] 주 CTA와 일반 버튼이 구분되는가
- [ ] 장식 요소가 핵심 정보보다 더 튀는가

개선: 화면당 핵심 강조 1개, 강조색은 주 CTA 전용, 보조 버튼 무게 낮추기(outline/텍스트 버튼), 크기·색·대비로 우선순위, 불필요한 배지·애니메이션 제거. 색만으로 구분하지 말 것(색각 이상 대응).

## 부록 B. 근거 있는 수치 기준

수치를 쓸 땐 아래처럼 출처를 함께 적는다. 목록에 없는 수치는 "경험칙"으로 표기.

| 항목 | 기준 | 출처 |
|---|---|---|
| 터치 목표 최소(iOS) | 44×44 pt | Apple Human Interface Guidelines |
| 터치 목표 최소(Android) | 48×48 dp | Material Design / Android 접근성 가이드 |
| 포인터 목표 최소(웹, AA) | 24×24 CSS px (또는 24px 원형 간격 확보) | WCAG 2.2 SC 2.5.8 Target Size (Minimum) |
| 포인터 목표 권장(웹, AAA) | 44×44 CSS px | WCAG 2.2 SC 2.5.5 Target Size (Enhanced) |
| 본문 텍스트 대비 | 4.5:1 이상 (큰 글자 3:1) | WCAG SC 1.4.3 |
| UI 컴포넌트·그래픽 대비 | 3:1 이상 | WCAG SC 1.4.11 |
| 키보드 포커스 표시 | 보여야 함 | WCAG SC 2.4.7 |

## 부록 C. 예시

### 예시 입력
> 이 결제 화면 UX 검토해줘. (모바일 앱 스크린샷) 상단에 쿠폰 배너 3개(각각 빨강·주황·보라 배경), 중간에 배송지·결제수단·포인트 사용·선물포장·영수증 설정이 같은 간격으로 나열. 하단에 '취소'와 '결제하기' 버튼이 같은 회색 크기로 붙어 있고, 결제하기 왼쪽 2px 옆에 '주문 삭제' 휴지통 아이콘.

### 예시 출력(요약본, HTML 파일에 들어갈 내용 구조)

#### 1. 한줄 평가
결제 버튼이 다른 요소보다 눈에 덜 띄고 삭제 아이콘과 붙어 있어, 핵심 행동을 찾기 어렵고 오조작 위험이 있다.

#### 2. 핵심 행동
- **핵심 행동**: 배송지·결제수단 확인 후 결제하기
- **현재 발견 가능성**: 낮음 — 원색 쿠폰 배너 3개가 시선을 먼저 가져가고, 결제하기는 취소와 같은 회색
- **방해 요소**: 쿠폰 배너, 동일 간격 옵션 나열, 결제 버튼 옆 삭제 아이콘

#### 3. 주요 문제
##### [Critical] 결제하기 바로 옆 '주문 삭제' 아이콘
- **적용 법칙**: 피츠의 법칙
- **위치/요소**: 하단 바, 결제하기 버튼 좌측 휴지통 아이콘(간격 약 2px, 스크린샷 기준 추정)
- **왜 문제인가**: 가장 자주 누르는 목표 옆에 파괴적 행동이 붙어 있어 엄지 오차 범위 안에 들어간다.
- **사용자 영향**: 결제하려다 주문이 삭제될 수 있음
- **수정 방법**: 삭제를 하단 바에서 빼서 상단 오버플로 메뉴(⋯)로 이동하고 확인 다이얼로그 추가. 하단 바에 남겨야 하면 최소 8dp 이상 떼고(경험칙) 터치 영역 48×48dp 확보(Material).

##### [High] 주 CTA가 보조 버튼과 시각적으로 같음
- **적용 법칙**: 폰 레스토프 효과
- **위치/요소**: 하단 '취소'·'결제하기'
- **왜 문제인가**: 같은 색·크기라 무엇이 주 행동인지 구분되지 않는 반면, 화면 상단 배너 3개는 원색이라 강조가 거꾸로 배분됨.
- **사용자 영향**: 결제 버튼을 찾는 데 시간이 걸리고 취소를 잘못 누를 수 있음
- **수정 방법**: 결제하기만 브랜드 강조색·전체 폭 버튼으로, 취소는 텍스트 버튼으로 낮추기. 쿠폰 배너는 중립 배경 한 줄로 축소.

##### [Medium] 결제 옵션 5개가 같은 간격·같은 무게로 나열
- **적용 법칙**: 힉의 법칙, 근접성의 법칙
- **위치/요소**: 중간 설정 목록
- **왜 문제인가**: 필수(배송지·결제수단)와 선택(포인트·포장·영수증)이 구분되지 않아 모두 검토해야 하는 것처럼 보임.
- **사용자 영향**: 결제 전 판단 시간 증가
- **수정 방법**: '필수 확인' 그룹과 '추가 옵션(접힘)' 그룹으로 나누고 그룹 사이 간격을 그룹 내부보다 2배 이상 크게. 선택 옵션은 기본값 표시 후 접기.

#### 4. UX 법칙별 점검표
| 법칙 | 평가 | 근거 |
|---|---|---|
| 힉의 법칙 | 개선 필요 | 필수·선택 옵션이 한 번에 노출됨 |
| 피츠의 법칙 | 문제 있음 | 파괴적 행동이 주 CTA에 붙어 있음 |
| 제이콥의 법칙 | 양호 | 하단 고정 결제 버튼은 일반적인 커머스 관례 |
| 근접성의 법칙 | 개선 필요 | 옵션 간 간격이 모두 같아 그룹이 안 보임 |
| 폰 레스토프 효과 | 문제 있음 | 강조가 배너에 몰리고 CTA는 무채색 |

**잘 된 점**: 결제 버튼을 하단에 고정해 엄지 도달 범위 안에 둔 점.

#### 5. 우선순위별 개선안
**이번 버전에 꼭 필요한 것**: 삭제 아이콘 분리, 결제하기 단독 강조
**다음 버전에서 개선해도 되는 것**: 옵션 그룹화·접기, 쿠폰 배너 축소
**현재는 제외하는 것이 좋은 것**: 결제 단계를 여러 화면으로 나누는 재설계(현재 문제는 최소 수정으로 해결 가능)

#### 6. 적용 예시
```
[수정 전]                      [수정 후]
┌──────────────────┐          ┌──────────────────┐
│[쿠폰][쿠폰][쿠폰] │          │ 쿠폰 2장 사용 가능 >│
│ 배송지            │          │ ▸ 필수 확인        │
│ 결제수단          │          │   배송지 / 결제수단 │
│ 포인트            │          │                  │
│ 선물포장          │          │ ▸ 추가 옵션 (접힘) │
│ 영수증            │          │                  │
│[취소][🗑][결제하기]│          │ 취소   [ 결제하기 ]│
└──────────────────┘          └──────────────────┘
```

#### 7. 최종 체크리스트
- [ ] 화면을 3초 보고 결제하기 버튼이 가장 먼저 보이는가
- [ ] 결제하기 버튼 주변 손가락 오차 범위에 삭제·취소가 없는가
- [ ] 결제하기 터치 영역이 48×48dp 이상인가
- [ ] 강조색이 결제하기 한 곳에만 쓰였는가
- [ ] 필수 확인 항목과 선택 옵션이 시각적으로 구분되는가
- [ ] 주문 삭제에 확인 단계가 있는가

## 부록 D·E. 템플릿 파일

|---|---|
